Diagnosis

The problem is not taste. It is that half the system was never built.

app/globals.css has a three-layer token architecture, 8 status tones × 5 roles, 13 domain enums mapped onto it, and a test that fails the build on any raw palette class. That work was done carefully and it is kept. What is missing is everything that would let a page use it consistently.

Today
  • A token layer and a primitive layer, with nothing between them — so every page re-types its own chrome.
  • tailwind.config.js extends only colors and fontFamily. No type scale, no spacing scale, no elevation, no radius — --radius is declared and consumed by nothing.
  • --primary, --link and --tone-info-solid are the same blue. Nothing on screen reads as a signal.
  • ~24 responsive utilities in the whole app. The sidebar is a hard w-64 with no breakpoint.
  • Six nav items, six tables, one per Prisma model. The IA is the schema.
Proposed
  • A composition layer — PageHeader, DataTable, FactRail, MoneyLine, PhaseStrip — each replacing a counted duplication.
  • Type, space, radius, elevation, motion and z-index scales, added the same way the colours were.
  • --primary becomes ink. Saturated hue then appears only where it means a status.
  • A real mobile layer: bottom bar, sheet nav, and tables that become cards instead of scrolling sideways.
  • An IA organised around work: what is blocked on me, what is blocked on the client, what is just a registry.
The signature

The phase strip

The most distinctive fact in this domain is that approval and payment are separate axes. A phase can be approved and unpaid; un-approving it must never un-pay it. That rule is already load-bearing in the schema and in the dashboard's revenue maths — but it has no visual form.

One device gives it one. Each segment is a phase, its width proportional to its price, its fill the phase-status tone, and a solid rule underneath where the money actually landed. Progress, weight and cash position in a single 10px object.

The underline is ink, not green, and that is the load-bearing detail. If "paid" were a green rule under an "approved" green fill, the two axes the device exists to separate would collapse back into one hue. Work state owns the colour; money owns the mark.

Shell & list pages

A pile is a segment, not a stacked block.

One rule does most of the work. Every named subset of a list becomes a mutually-exclusive segment on ?view=, counted in the control itself. Nothing that is a subset of a table renders above it.

That single rule deletes RequestPipeline and DecisionsCard as page furniture (each rendered verbatim on three pages today), collapses the three filter idioms on /tasks, and kills the ?status= vs ?queue= mismatch by construction — the requests page reads only queue, so four of the pipeline's five links currently navigate to an unfiltered list.

היום

The dashboard stops being a report about your own business.

Five identical KPI tiles measure five unrelated things, and three of them go neutral on a quiet day — so a calm morning renders as five grey boxes. You already know how many projects you have. What you don't know is which of eleven possible things is oldest and blocked on you.

Blocks 1–6 render only when non-empty — the same rule MorningBriefService already applies when it drops empty sections instead of printing eleven "אין" lines. The predicates get extracted into a shared today.service.ts so the brief and the screen cannot disagree.

Detail pages

One column of work, one rail of facts.

/clients/[id] is eleven full-width stacked cards in a single column, and it renders money three separate times in three different shapes — an aggregate band, a per-project/per-phase card, and again per row in the projects card. All three compute from the same helpers.

The fix is a placement rule, not a component rule. Money renders at exactly one granularity per page, and the granularity is the page's own noun. Client page → client totals. Per-project money → columns in a table you were already reading. Per-phase money → the project page only.

Mobile

The owner side currently does not have a mobile layout. At all.

sidebar.tsx is a hard w-64 h-screen with no breakpoint, no drawer and no hamburger, inside a flex h-screen overflow-hidden shell. At 375px it takes 256px and leaves 119px for the application — and the five list tables, 5 to 10 columns wide, scroll sideways inside that.

The fix is not a tuning pass. DataTable emits one data-slot, two elements: a <tr> on desktop and an <article> on mobile, both carrying the same data-testid and data-col hooks — which is what makes the table→card conversion a zero-spec-change event, and why the instrumentation commit has to come first.

Sequencing

Each phase ships on its own.

Ordered so that stopping after any phase leaves a working, better app. If the appetite turns out smaller than the plan, cut from the back, not from the middle.

  1. Instrumentation — zero visual change

    data-slot / data-testid / data-col on the table primitives and all five lists; aria-current on the sidebar; data-volatile on the clock. Then ~105 selector edits behind e2e/fixtures.ts, then CI (there is none today).

    Gate: the visual baselines must come back byte-identical. data-* and ARIA don't render — so this proves the commit is inert.

  2. Token scales & typographic hygiene

    Type, space, radius, elevation, motion, z-index. next/font. Delete the 25 redundant ml-2 icon margins — button.tsx already sets gap-2, so converting them to me-2 would preserve an 8+8px double gap. Add the RTL ratchet test.

  3. Primitives, piloted on /clients

    The full shape of the problem — list, search, table, detail, cards, money — at roughly a tenth of the blast radius: /clients is the smallest owner page and has no spec file at all. If the DataTable API is wrong, you find out on the cheapest page.

  4. Shell, navigation, mobile

    After the pilot (the sidebar and header are the components that most need the primitives), before the page grind (every page renders inside the shell). All six visual baselines invalidate here; the mobile Playwright project lands here.

  5. Page by page

    Contacts→leads, projects, tasks, requests, היום, then the orphans: login, the agent page (442 lines, in English, linked from nowhere), /settings, /money.

  6. Client portal, then cleanup

    The portal last — it is the best-built surface and the only mobile-first one. Mine it for patterns early; rebuild it late, or rebuild it twice.

The one risk worth repeating. The .tone-* rules sit outside @layer on purpose — inside it, Tailwind tree-shook all eight and every badge in the product rendered grey for weeks. New scales go in as theme.extend and :root properties only, never as hand-written utility classes. And npm run test cannot catch a recurrence: only npm run build runs the real purge.
