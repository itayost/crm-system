# 0001 — Product knowledge is precomputed cards, not live retrieval

Date: 2026-07-31
Status: accepted

## Context

The WhatsApp support bot needs to know what each client's product *is* — its
screens, flows, and vocabulary, in the client's Hebrew. It had three live
GitHub tools (tree, code search, file read) for this, and across every
production conversation it used them zero times. Even when used, they cannot
answer product questions: "אפשר לייצא דוח?" is not a string in the code.

Deep research (2026-07-31, recorded in the plan archive) compared live agentic
search, embeddings/RAG over code, and precomputed summaries. The coding-agent
consensus favours agentic search — but that consensus assumes code-level
questions and unbounded steps. A support agent answering fuzzy Hebrew product
questions under WhatsApp latency, against 8 small known repos, is the opposite
case. GitHub code search allows 10 requests/minute; one agent turn can burn
most of that.

## Decision

Each repo-configured project gets a **ProductCard**: Hebrew prose describing
the product (מה המוצר / מסכים / תהליכים / מילון / אינטגרציות / מה לא קיים),
generated by one model pass over the repo's deterministic surface — route
files, visible Hebrew strings, i18n messages, README — and injected whole
into the support prompt as a stable, prompt-cached block. A nightly SHA-gated
cron regenerates only repos whose HEAD moved. The owner's `manualNotesHe`
survive regeneration and win on conflict. The live GitHub tools remain as a
demoted fallback for implementation specifics only.

## Consequences

- The bot answers product questions from context, at zero marginal latency
  and near-zero marginal cost (cache reads).
- A card can be wrong until regenerated or corrected; the explicit
  "מה לא קיים" section and the owner-notes override are the guards.
- Products whose screens are not in `page.tsx` (the Android app) need their
  screens hand-written in `manualNotesHe`.
- Embeddings/pgvector were deliberately not adopted; revisit only if cards
  grow into a multi-document corpus per product.
